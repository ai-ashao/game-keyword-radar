> 修订日期：2026-09-11  
> 核对代码基线：`99f7f9e42cae7967f53ffde3c7b339eea08a9963`，V2 RC1  
> 定位：**Game Demand Radar + Keyword / Page Opportunity Research Workbench**  
> 状态：**待实施的开发规格，不代表 V2.1 已开发、已部署或已通过真实数据验收。**

## 1. 改造背景

### 1.1 继承的能力

原 V2 方案保留 Steam 扫描、Dashboard、历史快照、关键词规则、Google Trends 可选能力、Markdown 报告、CLI 与 Codex Skill，新增统一实体、跨平台信号、问题簇、Page Graph 与人工验证队列。本次继续复用这些模块，不推倒重写，不引入新的产品方向。[O1]

### 1.2 本次问题不是“数据源数量不够”

用户提供的运行截图中，CS2 获得 Demand 90、权重覆盖约 28%，只有 Steam 展示可用指标，24h / 7d 无可比样本，没有已采集的明确玩家问题。该截图只能说明这个游戏当次记录的状态，不能外推其他 79 个游戏的数据完整性。[U1]

核对 V2 RC1 代码后，可以确认以下机制问题：

| 环节 | 当前行为 | 对发现新机会的影响 |
|---|---|---|
| Steam 入口 | `top_sellers` 与 `popular_new` 混合后按榜单名次截断 | 新游没有独立候选保障 [R6] |
| 初步排序 | 使用 `score_demand()` 排序，直接取前 `deep` 个 | 规模大的成熟游戏优先占用研究预算 [R1] |
| 历史使用顺序 | 深度采集以后才 `attach_history()` | 已有增长历史未参与本轮深度初筛 [R1] |
| Steam 分值 | 在线规模、评论规模、新鲜度按 0.7 / 0.2 / 0.1 混合 | 老游戏前两项高，也可以拿到高分 [R2] |
| 缺失来源 | 按可用来源权重归一化 | 单平台高分容易被误读成综合机会高分 [R2] |
| Twitch | 已有 Top Games、全局流样本、单游戏查询 | 不是“没写 Twitch”，而是其定向观测没有前移到候选筛选 [R3] |

因此，接通更多 API 不能替代筛选纠偏。若仍按 Steam 玩家数和 Twitch 观看数取前十名，只是增加了一份热榜。

### 1.3 修订后的基本原则

**CS2 这类已知成熟游戏可以进入原始库、基准观察和已有站点研究，但没有新的增长、事件或问题证据时，不能仅靠规模进入默认今日机会和自动深度分析。**

同时，不采用“所有老游全部删除”“至少两平台齐全”“必须已有七天历史”这类会损失早期信号的统一硬门槛。

## 2. 职责边界冻结

### 2.1 核心问题

> **哪些游戏最近出现了值得进一步验证的新需求？为什么现在值得看？下一步应验证哪一个具体页面或关键词簇？**

本项目负责游戏发现、生命周期核实、变化监测、玩家问题、关键词假设、Page Graph、Preliminary Opportunity、Semrush / SERP 队列，以及 Existing Site vs New Site 路由。

“有潜力爆发”在界面中应表达为“早期信号”“持续增长候选”“待复核的注意力上升”。不输出爆发概率，不保证预测成功。

### 2.2 不负责的事项

小黑盒选题、公众号 / 社媒文章生成、标题生成、自动发帖仍属于独立 `game-content-radar`。两个项目不共享业务代码，不相互硬依赖，也不与 ShipLean 自动绑定。[O1]

不自动购买 API、自动买域名、自动建站或自动作出付费决策。

### 2.3 使用场景分离

默认工作台是“新机会发现”。“成熟游戏研究”和“已有站点扩页”保留独立视图。用户可以手动研究成熟游戏，但该操作不能把它伪装成算法发现的新游，也不能绕过 Semrush / SERP 验证。

## 3. V2.1 产品目标

### Q1：为什么这个游戏今天入选？

每条候选必须显示入选通道、具体触发证据、观察时间和下一项缺口。禁止只有“90 分”“很火”而无原因。

### Q2：它是哪一种机会？

采用两层分类，避免一个 `new` 同时代表“新游戏”和“本机第一次看到”。

| 维度 | 值 | 含义 |
|---|---|---|
| 生命周期 `lifecycle` | `new_release` / `established` / `preview` / `unknown` | 游戏所处发售阶段；不是本机扫描状态 |
| 入选通道 `lane` | `new_release` / `rising` / `new_demand` / `exploration` | 本次为什么值得分配研究预算 |
| 观察分类 | `monitor_only` / `excluded` | 保留观察，或明确排除；不是“零需求” |

初始新游窗口设为首次公开可玩发行后 **0–90 天**。这是可配置的候选定义，不是市场规律，也不是用户对“新网站”的年龄定义。超过窗口仍可因增长或新问题入选其他通道。

### Q3：规模、增长、传播和页面需求分别是什么？

分别显示当前规模、可比变化、传播广度、问题证据与页面机会。不再把这五件事压成一个醒目的总分。

### Q4：下一步做什么？

保留 `WATCH / VALIDATE / EXPAND_EXISTING_SITE / VALIDATE_NEW_SITE / SKIP`。`lane` 和行动状态是两个不同维度；入选不等于已验证，更不等于 Build。

## 4. 数据源架构

### 4.1 Steam：从“热度排名”改为“新游入口 + 玩家观测”

保留 Top Sellers、Popular New、App Detail、发行信息、Genres / Categories、Current Players。现有商店 `recommendations.total` 只作为评论规模代理，不能冒称已核实的全量评论。[R6]

**必须调整两个截断位置：**

1. 合并榜单前后都保留来源和来源内名次；原始发现记录不能因游戏未入前十名而丢失。
2. 元数据采集预算优先保护近期发售来源和待核实实体，不能先按绝对热度挑选要补详情的游戏，再声称已公平筛选。

Top Sellers 可以提供基准记录和老游复苏候选，但“位列 Top Sellers”本身不是新机会触发。

本地监测列表中的游戏即使从本次榜单移出，也可以按已知 appid 继续观测。**移出截断样本不等于热度归零，更不等于需求消失。**

Steam 在线人数按瞬时玩家观测展示。商店查询国家与玩家指标地域须分字段保存，不能因为商店参数为 US 就把玩家数标成美国玩家。[R6]

### 4.2 Twitch：作为核心发现和初筛来源

#### A. Steam → Twitch 定向路径

```text
近期发售 / 已进入观察列表的 Steam 游戏
→ 核实 Twitch game_id
→ 定向读取该游戏的直播样本
→ 与同口径历史比较
→ 决定是否进入深度问题研究
```

**不要求先进入 Twitch Top Games。**现有 `fetch(entity)` 的按游戏查询能力应前移或拆分复用，不必重写整套 Provider。[R3]

#### B. Twitch → 游戏实体反查路径

```text
Twitch 类别列表和历史观察列表
→ 对比排名区间、已有定向观测与新出现类别
→ 核实游戏身份、发行阶段和平台信息
→ 分到新游、增长、新需求或身份待核实通道
```

Top Games 提供热门类别入口，Games 提供 ID / 名称映射，Streams 支持按 `game_id` 过滤。它们不是“未来爆款列表”；默认不把全站前几页直播间汇总当每个游戏全量。[T1]

#### C. 必须保存的 Twitch 指标

| 指标 | 使用方式 |
|---|---|
| `observed_viewers`、`observed_live_channels` | 当前采集样本的观众与频道规模 |
| `top1_viewer_share`、`top3_viewer_share` | 样本集中度；样本不完整时不宣称全平台占比 |
| `non_top1_viewers` | 除最大直播间以外的样本观众，辅助判断扩散 |
| `broadcaster_ids` | 观测内去重、跨时间比较参与者；不采集私密资料 |
| `category_rank`、`rank_scope` | 指定类别列表快照中的观察名次和覆盖范围 |
| `sampling_scope`、`sampling_complete`、`page_limit` | 决定观测可否比较 |
| `window_started_at`、`window_finished_at` | 记录跨页采集窗口，避免伪装成同一瞬间 |

Streams 跨页结果可能变化，须去重并保留动态分页限制说明。成功消费全部返回页，也只是采集窗口内的观测，不是平台审计总量。[T2]

#### D. 不同采样范围不得混算增长

`global_top_streams`、多游戏混合过滤样本和 `game_streams` 是不同范围。给多个 `game_id` 一次取前 100 条仍可能被大游戏占满，不能当作每个游戏各自采满；默认定向观测按单游戏采集。

同口径的部分样本可显示“样本变化线索”，但不能单凭它认证全游戏增长。只有可比性检查合格的更完整观测，才进入“有可比增长证据”的判断；即便如此仍标记为观测，而非绝对事实。

#### E. 单主播峰值：标记风险，不直接淘汰

初始集中度提示阈值为样本 Top 1 > 70%。这是提示规则，不是爆发预测模型。

若仅有单次 Twitch 峰值且高度集中，进入早期观察或探索名额。若后续主播数、非头部观众持续增加，或 Steam 出现独立增长，再提升证据层级。不得仅因集中度高就忽略来自其他来源的有效增长。

赛事、Drops、试玩、推广等仅在有明确来源时标记；不能仅从峰值形状推定原因。标签用于解释关注性质，不自动判定“虚假需求”。

#### F. 缺少 Twitch 仍应运行

Twitch 是核心能力，但不是每个候选必须满足的硬门槛。未配置、认证失败、限流、无法匹配、没有开播记录和预算未采集必须分别显示；不能都简写为“无潜力”。

### 4.3 Google Trends：可选方向补强

保留 Official / Legacy Provider 抽象。官方 Alpha 仍需获得访问资格；没有资格或适配器时明确标记未接入，不把预留类描述成已经可用。[T6]

只能比较与同一 Provider、term/topic、地域、时间范围和归一化方式兼容的观测。不能把独立归一化曲线的指数直接拼接；不能把“相关查询”自动当作已验证的月搜索量。

Trends 的主要任务是补充搜索方向，失败不阻塞初筛和问题研究。通用游戏名存在歧义时，先核实实体，不盲目查询 codes / tier list / map。

### 4.4 YouTube：答案型内容证据，不承担冷启动发现门槛

保留 `search.list → videos.list` 流程；近期攻略、Build、问题解决内容属于内容需求代理，不等于玩家问题原话或 Google 搜索需求。[T4][T5]

只对已选深度候选执行有玩法依据的查询，保留采样时间、查询、地域、语言、去重方式和视频发布时间。查询到的视频数量不是平台全量。

`view_velocity_proxy` 应标成“累计播放 / 上线时长代理”，不冒称最近两小时真实新增播放。缺少 API Key 时，Steam / Twitch 初筛仍然工作。

### 4.5 Reddit：问题证据，而非泛热度

保留公开 RSS 的 best-effort 实现和专属 subreddit 配置，继续区分真实问题与视频内容代理。当前代码并未实现可靠的自动专属社区发现，不把该能力写成已完成。[R8]

有日期的近期问题、不同作者的重复问题可作为老游新需求入口。旧问题第一次被本机采到，不能自动标记为最近才出现的需求。没有日期的证据可供人工核实，不进入新事件确认。

403 / 429、无匹配记录、预算耗尽和未配置社区分别展示。不得绕过访问限制；本版本不引入代理、反检测或付费 Reddit 依赖。

## 6. 统一游戏实体与生命周期

### 6.1 匹配规则继续保留

明确平台 ID → 唯一完整名称 → 唯一规范化名称 → 经核实的别名。模糊匹配只给建议，不自动合并、不覆盖已有 ID。多个匹配或重名进入待核实状态。[O1]

Twitch 类别不一定是游戏。非游戏类别排除应结合类别元数据、维护列表和人工纠正；`igdb_id` 缺失不等于不是游戏。无精确名称匹配不等于 Twitch 没有该游戏。[T1]

### 6.2 发售时间与首次发现时间必须分开

```text
first_seen_at                 本雷达首次记录，不证明游戏新旧
first_seen_by_source          各来源首次被本机记录的时间
platform_release_dates        各平台展示的发行日期及来源
first_public_playable_at       有证据支持的首次公开可玩日期；可为空
release_stage                 released / early_access / demo / upcoming / unknown
release_date_basis            verified_public / platform_reported / manual_verified / unknown
lifecycle                     new_release / established / preview / unknown
recency_status                verified / provisional_platform_date / unknown
```

首次公开发行无法确定时，保留“平台发售日期候选”，不要强行写成全球首发。新平台移植、旧 app 改名、抢先体验转正式版不自动重置全球游戏年龄；有明确变化时可建立 `release_event`。

Demo / 未公开发售游戏进入预发布观察，不与已发行游戏的 Steam 当前玩家混用。若一个主体存在 Demo appid 与正式 appid，分别保存平台记录和关系，不能仅因标题相近就混算玩家数。

### 6.3 生命周期规则

使用注入的 `as_of` UTC 日期，不在测试中隐式依赖机器今天。

- 已确认公开可玩，距首次公开可玩日期 0–90 天：`new_release`。
- 已确认早于该窗口：`established`，仍可出现增长或新需求。
- 明确试玩 / 未发售：`preview`，不声称已形成上线后玩家规模。
- 日期缺失、来源冲突或首次公开发行未核实：`unknown`；可进入探索，不强制排除。

**冷启动不能以“先人工核实全球首发”为统一前置门槛。**若可信平台资料显示90天内发行、阶段为已公开可玩，并且没有更早发行、移植、重命名等已知反证，可以先进入 `new_release` 通道，标记 `recency_status = provisional_platform_date`，主文案为“平台近期发行，首发待核实”。生命周期仍可为 unknown；通道表示研究原因，不是已确认事实。组内排序低于发行已核实者，但不挤到仅有的探索名额。

完全没有发行日期、日期冲突或明确预发布的候选继续走探索 / 预发布观察。发现更早发行证据后修正后续分类，保留原快照判断。不得以“第一次扫描 CS2”触发新游标签。

## 7. V2.1 数据模型

### 7.1 兼容策略

保留 `ScanSnapshot.schema_version = 2` 的既有结构，新增 `analysis_version = "2.1"`、`selection_policy_version` 和可选扩展字段。旧字段不删除，旧文件不改写。若实施时需要破坏性变更，必须另行升级 schema，不静默复用字段含义。

旧快照没有生命周期或筛选结果时，新 UI 显示“历史版本未记录”，不能补猜成新游、零分或稳定。

### 7.2 GameEntity 扩展

在现有名称、别名、平台 ID、玩法基础上增加第 6 章的日期、阶段和来源信息。另加 `last_observed_at`、`last_deep_analyzed_at`、`manual_labels`。发售事实与当次算法分类分别保存。

### 7.3 PlatformSignal 扩展

新增 `observation_id`、`metric_scope`、`scope_version`、采集窗口和结构化失败原因。复用缓存必须保留原 observation_id 和原始采集时间，不以新的 scan run_id 伪造新样本。

`sample_only`、`sampling_complete`、`cache_hit` 和来源是否配置是不同概念。零值仅来自成功且对应范围确实观测到零的响应。

### 7.4 MomentumAssessment

```text
state: unknown / early_signal / rising / stable / falling / mixed / inconclusive
period: intraday / 24h / 7d / none
comparisons[]:
  source, metric, current_value, baseline_value, absolute_delta
  percent_change, comparison_kind, comparable, limitation
  current_observation_ids, baseline_observation_ids
persistence: untested / single_spike / sustained_observation
breadth: unknown / concentrated / broadening / distributed
rising_sources[], conflicting_sources[], limitations[]
```

`stable` 必须有可比历史支持。没有历史使用 `unknown`，不能因为没有计算出上涨就标为稳定或下跌。

### 7.5 SelectionDecision

```text
eligible_lanes[]
primary_lane
decision: selected / monitor_only / deferred_budget / excluded
reason_codes[]
trigger_evidence_ids[]
missing_evidence[]
selected_for_monitoring
selected_for_deep
selection_order
policy_version
as_of
```

一个游戏可符合多个通道，但一次深度扫描只占一个名额。每次未入选都要区分：没有触发、预算延后、手动忽略、实体未核实或明确不是游戏。

### 7.6 QuestionCluster / PageOpportunity

保留原 V2 模型、稳定页面 ID、关键词下层兼容、证据触发、维护成本与站点路由。[O1]

补充 `evidence_level`、`trigger_freshness`、`event_id`（如适用）。`question_count` 仅计真实问题；视频内容代理单独计数，不把“视频标题含 guide”说成玩家已经提出的重复问题。

### 7.7 ScanSnapshot 与 MonitoringSnapshot 分离

完整扫描快照增加 `selection_summary`、`selection_decisions`、各通道预算、实际用量、延后原因与比较规则版本。

轻量监测使用独立 `MonitoringSnapshot`，只保存新观测、来源状态和范围，不覆盖最近完整报告，不重写人工验证，不强制运行 Page Graph。两种记录共用 observation_id 去重和历史读取接口。

## 8. 新 Pipeline：历史比较前置，先准入后深度

### 8.1 总流程

```text
1. Load：实体库、人工排除、观察列表、可用历史、配置版本
2. Discover：Steam 两路来源 + Twitch 类别入口 + 已跟踪实体
3. Resolve：平台 ID、别名、非游戏排除、发售信息核实
4. Basic Observe：有预算保障的 Steam 玩家 / Twitch 单游戏轻量观测
5. Compare：先接入可比历史，再计算早期变化与传播特征
6. Admit：生命周期 + 新触发 → 四个通道；成熟无触发 → monitor_only
7. Allocate：按通道分配 Deep N，去重、冷却、轮转、记录落选原因
8. Deep Enrich：入选游戏才查询 YouTube / Reddit / 可选 Trends
9. Reassess：更新问题证据和行动，不倒填初筛时不存在的证据
10. Page Graph：产生可解释页面节点与 Existing Site 路由
11. Queue：进入人工 Semrush / SERP 验证
12. Persist：快照、筛选日志、报告、Dashboard
```

禁止在第 5 步之前使用 `sorted(demand)[:deep]`，也不能在第 3 步之前按规模丢掉所有新游入口。

### 8.2 两个入口都必须可独立发现候选

Steam 新游不在 Twitch Top Games，也能获得定向观测。Twitch-only 游戏没有 Steam appid，也可进入探索或增长通道。API 未配置时保持部分运行，分别说明缺少什么。

### 8.3 四通道准入规则

| 通道 | 至少需要的触发 | 不要求什么 |
|---|---|---|
| `new_release` | 有来源的近期发行信息（可带首发待核实标记）+ 至少一个初始关注 / 玩家观测 | 不要求七天历史，不要求 Steam 与 Twitch 同时强，不要求先完成全球首发考证 |
| `rising` | 至少一个来源有可比的增长线索；部分样本只能低级别入选 | 不要求属于新游，不要求所有来源一致 |
| `new_demand` | 近期可定位的问题 / 内容事件，有明确页面意图 | 不要求整个游戏热度上涨 |
| `exploration` | 新游信息待核实、预发布、单主播触发、微弱苗头等可解释线索 | 不要求达到正式增长门槛；有独立的小额预算 |

已知成熟游戏若只有当前在线多、观看多或累计评论多，归 `monitor_only`。名称在黑名单不是主要方案；必须用可核查的生命周期和触发证据做判断。

`new_demand` 的证据可来自已有快照或人工加入的近期问题。不能要求“先完成本轮 Deep 才准入 Deep”。新证据在本轮深度采集后出现时，更新后续行动和下一轮通道，保留原入选理由。

### 8.4 近门槛机会与冷启动

门槛未达到的游戏仍保留原始记录，显示距离条件的差距，可进入探索和下一轮监测。不开启“必须全部满足”的隐性筛选。

第一天可用：近期发行入口、已有静态发行证据、Twitch 定向观测、人工种子和独立探索名额。没有历史的成熟游戏不自动获得增长资格；没有历史的新游也不会被全部排除。

### 8.5 成熟游戏重新入选

成熟游戏可因以下任一明确变化重新入选：可比玩家 / 注意力增长，近期更新产生具体新问题，新的模组 / 工具需求，人工提供待验证的独立页面意图。重新入选只表明该变化值得研究，不改写其发行年龄。

### 8.6 推荐原因必须可回放

保留 `before_deep_selection` 与 `after_deep_assessment`。回放时只能使用当时已经存在的证据；不能用后一天的游戏表现证明前一天“提前发现”。

## 9. Demand Momentum：拆分热度、增长与研究排序

### 9.1 撤下混合总分作为初筛依据

原 25 / 20 / 15 / 15 / 15 / 10 权重定义及当前归一化 Demand 分保留为历史兼容说明，不再用于默认新机会准入和 Deep N 选择。[O1][R2]

V2.1 默认展示：**生命周期、当前规模、增长状态、传播特征、来源覆盖、具体问题证据**。不新增一个同样混杂的“爆发潜力 90 分”。

历史 Demand 90 可以在“旧版本研究分”折叠区查看。它不能被重新命名为“90% 爆发概率”。仅 Steam 可用时，主视图写“1 / 5 个来源；仅 Steam”，权重覆盖 28% 只作为兼容诊断，不当准确率。

### 9.2 比较原始值与比较资格分别保存

每个来源先检查同实体、同指标定义、同地域 / 语言口径、同采样方式、相同查询 / 预算范围、相同测量版本、真实不同观测时间。

不同缓存 run、缺失响应、不同 Twitch 范围、YouTube 查询集合变化、平台切换、人工补数据不直接形成增长。Steam / Twitch 等当前量才可按其量纲比较；累计评论规模不替代近期玩家变化。

### 9.3 24h / 7d 与日内苗头

建议规则版本 `selection-2.1-r1`：

- 轻量采样目标间隔 2 小时，测试和本地调度可配置。
- 日内苗头：至少 3 个非缓存重复观测，跨度至少 4 小时；不足时为 `unknown` 或单次触发。
- 较可信的 24h / 7d：最近 6 小时内至少 3 个独立观测，与平移 24 小时 / 7 天的窗口配对，当前窗口跨度至少 4 小时；一对一匹配，不重复借用同一基线。
- 24h 配对容差初始 ±1 小时，7d 初始 ±2 小时；保留实际时差。星期 / 时段差异作为解释，不用任意前一次扫描冒充日同比。
- 使用配对后的当前值中位数与基线值中位数计算变化，降低单次尖峰影响。
- 只有一个合适点对时，可展示“点对变化”，证据级别不足以独自标为持续增长。

现有宽容差点对算法可保留为旧快照展示，但不可在 V2.1 中静默当成新窗口证据。[R4]

### 9.4 低基数与百分比

设当前窗口代表值为 C、基线为 B：`absolute_delta = C - B`。

当 B > 0 且满足对应基数要求时，`percent_change = (C - B) / B × 100`。B 为零时百分比为 null，显示“从 0 到 C”；极小基数显示绝对变化和 `low_base`，不能把 2 → 20 的 900% 当主要排序优势。

用于起量线索的初始参数如下，仅用于分层，不是自动删除线：

| 来源 / 指标 | 基线建议下限 | 相对上升 | 绝对上升 | 处理 |
|---|---:|---:|---:|---|
| Steam 玩家 | 100 | ≥40% | ≥200 | 合格可比窗口形成增长线索 |
| Twitch 样本观众 | 100 | ≥40% | ≥100 | 部分样本只形成带限制的线索 |
| Twitch 频道 | 5 | ≥50% | ≥3 | 用于传播广度；不可冒充观众需求 |

低于基数但出现明显新增规模，进入 `early_signal` / 探索，安排复查，不输出无穷百分比，也不直接淘汰。Steam 250 玩家、Twitch 100 观众或 3 个频道可作为新游初始关注的默认触发之一；三者是 **OR**，不是 AND。低于这些值的新游仍可进入探索。

### 9.5 Momentum 状态判定

1. 没有可比数据：`unknown`；有单次峰值、低基数增长或仅日内苗头：`early_signal`。
2. 至少一个来源有合格的多点可比上涨：`rising`，注明单源或多源；仅 Twitch 高集中单峰不独自提升为持续扩散。
3. 存在明确相反方向：`mixed`，并列来源变化；不平均相消后给“平稳”。
4. 有合格可比数据、基线不低且变化处于初始 ±10% 方向死区：`stable`；有多点可比下降且达到第 9.4 节同来源相对 / 绝对阈值的负向对称强度：`falling`。
5. 有变化但落在方向死区之外、未达到强度或持续性要求时，保留原始变化并使用 `inconclusive`；有具体正向早期触发可用 `early_signal`。不能把所有尚未满足 rising 的情况改成 stable。
6. 上述合并优先级：有效方向冲突 → mixed；否则合格上涨 / 下降 → rising / falling；否则明确早期正向触发 → early_signal；否则所有合格方向都在死区 → stable；其余已有可比但不充分 → inconclusive；无比较也无触发 → unknown。缺失来源不参与多数投票。

持续性与传播广度是独立标签。`rising` 可以是单源增长，不等于已形成广泛传播，也不等于 Google 搜索量增长。

### 9.6 分组内排序，不再用全局热度吞掉名额

选择阶段首先使用第 16 章的通道名额；每组内部采用可回放的排序键，不使用混合 Demand 总分：

| 通道 | 组内优先顺序 |
|---|---|
| 新游 | 发行身份可信度 → 已有增长证据等级 → 证据新鲜度 → 等待时长 |
| 增长 | 多点可比优先于点对 / 部分样本 → 持续性 → 传播扩展 → 新鲜度 |
| 新需求 | 具体近期问题 → 真实问题优先于内容代理 → 重复性 → 已有站点适配 |
| 探索 | 有明确种子原因 → 尚未深度分析 → 最久未采样轮转 |

对全部并列项最后以稳定 slug 排序，保证测试确定性。绝对规模最多用于同组同证据级别的末级辅助，不改变准入或跨组名额。

Deep 后的“页面研究优先级”与此选择排序分别保存，不能用事后 Page Score 解释事前名额。

### 9.7 跨平台确认

Steam 玩家、Twitch 注意力与搜索 / 问题信号同向，可增加解释支持；缺失不是反对。一个平台有观众和频道两个指标仍是一个平台，不算“两平台确认”。同一条视频 / 社区转载不能伪装成多个独立用户问题。

V2.1 不用“至少两平台齐全”阻塞进入人工验证。页面是否值得人工验证，应以具体需求和待解决问题为依据。

## 10. Page Opportunity Score

保持与游戏状态分离，沿用原方案的页面证据、意图、页面图谱、可实现性、维护成本和证据质量框架。[O1]

| 维度 | 分值上限 | 本次调整 |
|---|---:|---|
| Problem / Query Evidence | 20 | 真实问题与视频代理分开计数 |
| Search / Page Intent | 20 | 仍需匹配实际机制，不能模板凑数 |
| Page Graph Breadth | 15 | 去重后的不同意图，不按同义词膨胀 |
| Build Feasibility | 15 | 保留 |
| Maintenance Cost | 10 | 保留 |
| Game Demand Contribution | 10 | 不再直接引用旧混合 Demand 分 |
| Evidence Confidence | 10 | 根据出处、日期、实体、重复性，而非“平台亮了几张卡” |

`Game Demand Contribution` 初始按已取得证据记分：有效持续增长最多 6，只有早期线索最多 3，两者不叠加；已核实近期发行最多 2；至少两独立来源有合格同向增长最多 2。缺失子证据保存 null，未取得的支持不授分，但不解释成“证明需求为零”。

`raw_score` 为已取得支持与规则项之和，不因缺失项重新归一化到满分。`score = min(69, raw_score)` 继续作为预验证展示。纯玩法假设应明确标记，不与已经观察到的问题页面混计。

无 Semrush / SERP 验证不得输出自动 Build。真实搜索量 0 是可记录的测量结果，不等于可以伪造非零，也不自动替用户作商业判断。

## 11. Page Graph：证据触发，不靠模板制造新机会

继续要求每个节点具备 **WHY THIS PAGE EXISTS**，保留玩法、问题、来源、时间和推测标记。[O1]

Codes 必须有兑换码机制或明确相关证据；Tier List 必须有可比较对象和比较意图；Map / Locations 必须有相关世界 / 位置需求；Builds 必须有对应系统；Calculator / Tracker / Tool 必须有可重复计算、查找或跟踪任务。

本次增加：

- 成熟游戏不能因为旧模板生成了一个“best settings”页面，就自动获得“新需求”通道。
- “新页面 ID”不等于“新需求”；需检查来源内容日期、主题是否首次出现于该版本、是否只是重新抓取。
- 没有外部证据但玩法支持时，可保留少量 `hypothesis`，列入假设库，不把它们算作已观察需求。
- 同一问题的不同措辞归同一意图；关键词只是验证种子，不是已证实的搜索量。
- 视频来源标记 `observed_content_proxy`，玩家问题标记 `observed_question`，两者都保留原链接。

Page Graph 为空是合法结果。应展示“尚无具体页面证据”，而不是为了凑满首页给所有游戏发同一套页面。

## 12. Existing Site Routing

保留默认规则：Workshop / SteamCMD → WorkshopFetch；通用游戏 Calculator / Tracker / Planner → GameKitHQ；明确 Fortnite Sprite 意图 → FN Sprite Hub。[O1]

**路由在具体页面层发生，不是筛选豁免。**不能因为已有 GameKitHQ，就把所有成熟游戏的假设工具页自动升为 `EXPAND_EXISTING_SITE`。

## 13. Dashboard V2.1 信息架构

Dashboard 仍是日常入口，不退回 CLI-first。本轮优先把已存在界面的信息和行为改对，不先做与实际功能脱节的高保真重设计。[O1]

### 13.1 首页改为“今日新机会”

主视图包含新游、增长、老游新需求三个明确区域；探索候选单列，不能用低证据探索数量充当验证机会数量。

卡片至少显示：游戏名、发行 / 生命周期、入选通道、WHY NOW、增长证据、问题证据、来源数、行动。旧 Demand 数字移到兼容详情，不做主视觉。

```text
新游观察｜Example B
平台近期发行，全球首次发行待核实
WHY NOW：Steam 日内玩家增加；Twitch 开播频道出现扩展线索
增长：早期信号，尚无 24h 基线
来源：2 / 5；问题证据：待深度采集
行动：WATCH → 补充攻略 / 问题证据
```

上例为设计占位，不是实时记录。

### 13.2 完成摘要改为筛选漏斗

```text
原始发现 X 条 → 去重实体 Y 个 → 轻量观测 Z 个
本轮符合入选条件 A 个 → 分配深度 B 个 → 可人工验证 C 个
其余：成熟无新触发 D、预算延后 E、身份待核实 F
页面：真实问题 P、内容代理 Q、玩法假设 R
```

各数值均从结构化结果计算，并给出去重口径；同一实体不在多个互斥去向重复计数。允许 C=0。此时显示是没有触发、证据不足还是来源故障，不用常青大游戏补位。

### 13.3 游戏详情

顶部不再写单独的“DEMAND 90”，而写：

```text
生命周期：成熟游戏
当前规模：有 Steam 观测
增长状态：基线不足
入选判断：只有规模证据，本次不占自动深度名额
具体问题：尚未获得
```

CS2 截图对应这种说明时，仍可手动查看、加入观察、研究已有页面；不能把“本次不推荐”写成“没有价值”。

五平台卡片保留当前值、数据时间、状态和限制。来源地域、观测范围、样本标记、实际时间间隔不得隐藏。

### 13.4 验证队列

保留待 Semrush、待 SERP、验证完成、Skip。允许手动加入任何有明确理由的页面研究；自动推荐与人工加入分开。

版本、初始入选证据、后续验证证据分别显示。Build 仍需填写现有的必要验证字段，不能因为游戏处于 rising 就自动放行。

### 13.5 历史与已知统计缺陷

本轮必须一并修复：

1. V2 摘要使用 `entities` 与 `page_opportunities` 计数，V1 使用旧字段；Twitch-only 游戏不得被统计为 0。[R7]
2. 相同分数 / 排名不再全部标记 `changed`。新增 `unchanged`，分别统计分数变化、排名变化、页面变化；不使用列表长度冒充“分数变化数量”。[R4]
3. 比较前检查 analysis / policy / scope / source eligibility；规则或样本范围改变时，不把分差解释成需求涨跌。
4. 没入本轮样本写“未覆盖 / 移出本次样本”，不等于游戏下线或需求消失。

### 13.6 观察与诊断

提供常青 / 成熟观察列表、近门槛候选、预算延后、数据源诊断。开关和理由在浏览器可见；不要求用户查看 JSON 才知道为何没有候选。

## 16. 请求预算与性能：发现 / 监测 / 深度三层

### 16.1 Stage A — Broad Discovery

采集分来源列表和已有观察项，保存原始候选。初始每个发现列表最多 100 行；该上限是请求和覆盖预算，不是“只允许 100 个有潜力的游戏”。

对缺少详情的条目提供元数据预算，初始每轮最多 80 个新 / 过期实体详情。分配比例建议 60% 近期发行入口、20% 已有有效触发 / 观察项、20% Twitch-only / 未核实实体轮转；重复实体只请求一次。缺额可在其他有理由的组间复用，不按热度自动补旧游。

原始采集行数、元数据补全数与活动监测池大小是三个独立统计量，不能混叫“候选数量”。

### 16.2 Stage B — Lightweight Monitoring

初始活动监测池最多 80 个游戏；针对已知 ID 采集 Steam 玩家与 Twitch 单游戏观测，静态详情用缓存。Twitch 采集本身也有预算，不能把“轻量”理解成免费无限请求。

活动池的预分配使用已存在的历史、发行入口和轮转，不依赖尚未采到的新指标。已知成熟无触发项不自动占高频活动池；保留原始榜单记录或显式低频观察，不能挤掉新游定向探测。

每轮 Steam 请求尝试预算建议 260、Twitch 建议 260；包含列表、映射、Token 相关请求、分页和失败重试，分别记账。每游戏 Twitch 初始最多 3 页。若预算不足，轮转延后，不把未采到当零。

Twitch 同一个游戏在同一采样轮完成有效观测后，进入 Deep 不重复获取同一套指标。其余来源不在轻量模式无脑重跑。

### 16.3 Stage C — Deep Enrichment

默认最多 10、最大 30，查询 YouTube / Reddit / 可选 Trends，并生成问题与页面。默认 10 个名额分配：

| 通道 | 初始名额 | 目的 |
|---|---:|---|
| `new_release` | 4 | 保护新游，不被规模挤出 |
| `rising` | 3 | 捕捉已有可比增长，不限年龄 |
| `new_demand` | 1 | 捕捉成熟游戏具体的新问题 |
| `exploration` | 2 | 留住早期、弱信号、日期未知候选 |
| **合计** | **10** | 只在有合格候选时使用 |

不同 Deep N 按 4:3:1:2 最大余数法分配整数名额；余数相同按表中顺序，N=0 不执行深度分析。多通道候选的主通道优先级为：新游 → 新需求 → 增长 → 探索，同时保留其他标签。

先按初始名额取组内候选，再将剩余名额依次给予新游、增长、新需求、探索的未选条目。探索最多占 `ceil(0.4 × N)`，可以少于 N，不得用没有触发的成熟游戏填满。

同实体只占一次；手动强制研究也占明确的手动 / 本轮预算，不隐藏在自动名额之外。默认自动 Deep 冷却 24 小时；出现新的有效触发或人工请求可提前重分析，仍记原因和预算。仅重复读同一缓存不算新触发。

### 16.4 本地运行频率

建议轻量采样每 2 小时、完整深度分析每天 1–2 次，均是可调的试运行起点，不是已经启用的自动化。

首版实现一次性 `monitor-once` 和在本地服务存活时可明确启停的简单循环即可，不引入任务队列或云调度。用户须主动开启定时监测；关闭服务、电脑休眠期间不会继续采集。恢复时标记缺口，最多执行一轮到期任务，不补造休眠期历史。

### 16.5 配额与失败

保留 YouTube 现有调用次数账本：每次搜索请求、每日搜索请求、视频详情请求分别预算；具体远端配额以当前官方文档和项目控制台为准，不硬编码过时的换算规则。[T4][T5]

Twitch 根据响应限流头和错误状态退避；重试有上限，不绕过服务限制。[T2] 缓存命中不重复消耗网络调用计数，但不能作为新的增长观测。

## 19. Codex Skill 改造

`game-keyword-scan` 从“解读高分游戏”改为“检查入选理由与页面需求”。[O1]

## 20. 评分与事实边界

继续执行原方案的八项事实约束，并补充本轮场景。[O1]

1. 缺失数据不等于 0；没有历史不等于稳定，没有上榜不等于没有观众。
2. 平台指标各自有量纲，观看数、玩家数、播放数不直接相加。
3. Twitch 注意力不是搜索意图；YouTube 内容代理不是真实用户问题次数。
4. Trends 方向不是搜索量；不同归一化范围不可直接拼接。
5. 首次发现不是首次发售；平台发行不是自动等同全球发行。
6. 总规模与增长分别展示；采样不完整不能伪装成全量。
7. 近期内容不必然代表新需求，需记录来源日期和触发依据。
8. 无 Semrush / SERP 验证，不输出自动 Build；分数不是成功率。
9. 截断、缺少凭据、预算延后不是负向需求证据。
10. Demo、合成回放、真实联网三种验收必须分开报告。
11. 阈值和名额比例是可校准假设，不写成已经预测有效。
12. 算法判断为“无新触发”不等于该游戏没有商业价值；保留人工研究入口。

## 21. 建议的行动状态

保持原状态名，修订触发条件，避免把平台数量作为统一硬门槛。

| Action | 适用条件 | 不代表什么 |
|---|---|---|
| `WATCH` | 早期信号、身份待核实、历史不足或具体问题不足 | 不代表零需求 |
| `VALIDATE` | 有可解释入选理由，并有具体页面 / 查询值得人工检查；单源也可成立 | 不代表已经有可靠 Google 搜索量 |
| `EXPAND_EXISTING_SITE` | 可定位需求适配已有站点，优先人工验证该页面 | 不代表跳过竞争和维护成本检查 |
| `VALIDATE_NEW_SITE` | 多个不同页面意图形成有依据的主题结构，已有站点不适合承接 | 不代表已经决定建站 |
| `SKIP` | 人工决定跳过，或明确不可承接 / 身份无效等有证据原因 | 不因某 API 未配置而触发 |

`monitor_only` 是选择去向，不新增为替代 Action；成熟无触发可以保留 WATCH，但不显示在今日自动机会主列表。

`VALIDATE_NEW_SITE` 要看不同用户任务，而不是同一词的四种写法。跨平台支持可提升优先级，不作为所有候选唯一通行证。

## 22. Dashboard 北极星与校准

北极星继续是：**今天哪些游戏值得花 10–20 分钟继续做 Semrush / SERP 验证？**[O1]

“理想每天 3–10 个”保留为体验期待，不设为硬指标。真实结果可以少于 3 个或为 0，不能为凑数把成熟榜首重新推荐。

本轮效果观察采用可解释的运营指标，不先承诺爆发预测准确率：

| 指标 | 统计口径 |
|---|---|
| 成熟无触发误入率 | 今日自动精选中，已知成熟且没有有效新触发的数量 / 自动精选数量 |
| 预算利用与分布 | 各通道实际 Deep 数、延后数、探索占比 |
| 人工验证有用率 | 人工完成检查的候选中，确实有具体可继续研究页面的比例；显示样本数 |
| 噪声原因 | 单主播、赛事 / 活动、实体错配、低基数、采样变更等，经核查记录 |
| 发现到验证时延 | 首次有效触发到人工验证完成的间隔，不与发行年龄混淆 |
| 重复推荐率 | 没有新证据但重复进入 Deep 的实体占比 |

运行一至两周后做首次参数复盘：同时检查入选与近门槛样本，避免只看成功案例。回放只能使用当时可见信息。未系统观察过的游戏集合无法计算全市场召回率，不能以未上榜样本充当完整负例。

| A36 | 只变排名 / 只变页面 / 换策略版本 | 分别计数；策略分差不称需求涨跌 |

| A40 | 配置含未知section/key、非法比例 | 明确报错，不能静默使用旧规则 |

### 24.2 API / 界面验收

验证来源失败原因、Token 脱敏、请求次数与缓存、筛选漏斗口径、各分组分页、详情解释、观察列表、验证队列、历史下载和 Markdown 报告的一致性。

桌面和移动端必须可以读出 WHY NOW、数据时间、部分样本与缺失状态；不以巨大的分数淹没限制。浏览器检查与真实来源请求验收分开记录。

### 24.3 真实来源验收分层

| 层级 | 必须提交的证据 | 不可替代项 |
|---|---|---|
| L1 冷启动核心链路 | 真实 Steam 与 Twitch 分别有可用观测；至少一个已核实实体完成 Steam→Twitch 定向链路；保存实际筛选日志 | Token / HTTP 200 / Demo 均不能替代 |
| L2 多次与跨日 | 相同实体同范围的独立观测；有满足规则的点对 / 多点证据，或如实标记缺口 | 不需要真实游戏必须上涨；正确识别稳定也算逻辑证据 |
| L3 页面证据 | 真实 YouTube 可用内容代理；Reddit 有则记录，失败则说明；问题与假设计数正确 | 模板生成不替代真实内容 / 问题来源 |
| L4 业务行为 | 当前高规模成熟无触发项不占今日精选；人工检查入选及近门槛样本 | 不以测试数量或抓到80款游戏当有效性证明 |

原 V2 要求的真实 Steam + Twitch + YouTube 联合验收继续保留。L2 未满足时不得宣称增长能力已实测通过；冷启动功能可以单独报告通过。找不到自然上涨案例时用合成回归验证算法，并在真实层报告当时实际方向，不伪造上涨游戏。[O1]

### 24.4 上一版测试结果的使用方式

V2 RC1 的历史测试记录只能作为旧版证据，不能直接算作 V2.1 通过。新验收记录必须包含新 commit、配置版本、运行时间、测试结果、真实 run_id、来源状态和未通过事项。

## 25. V2.1 明确不做

不做机器学习爆款预测、付费历史数据库、全量 Twitch 直播抓取、代理反检测、云 SaaS、多租户、用户系统、内容生成或自动建站。

不建立一份“老游戏永远不许入选”的庞大名称黑名单；不把新增 API 数量作为进度；不添加与筛选无关的大型后台；不要求为每个平台构建复杂统计模型后才让用户使用冷启动观察。

延期项明确包括：自动全网查首次发售、自动发现所有专属 subreddit、完整因果归因、赛事 / 推广自动识别、真实历史回测意义上的预测准确率。V2.1 提供证据字段和手工纠正，不宣称已实现这些能力。

## 26. 最终产品定义

> **以 Steam 与 Twitch 双向发现和持续观测为核心，先识别新游、增长与新问题触发，再使用 YouTube、Reddit、可选 Trends 补充证据，形成可人工验证的 Keyword / Page Graph。**

完整工作流：

```text
Steam 新游 / Twitch 类别 / 本地观察列表
→ 核实实体、发行阶段和实际采样范围
→ 持续观测与可比历史
→ 新游 / 增长 / 老游新需求 / 探索分组
→ 有预算保障的 Deep Analysis
→ 问题证据与 Page Graph
→ Existing Site 优先路由
→ Semrush Keyword Graph
→ Google SERP
→ 人工 Build / Skip
```

**衡量这次升级的方式不是“CS2 分数降了没有”，而是“成熟游戏没有新触发时不再挤占新机会，新游尚未上热榜时仍有被发现、观察和验证的路径”。**
